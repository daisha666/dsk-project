# dsk_Project 開発指示書（Claude Code貼り付け用）

## 0. これは何か
既存の「競馬予想2」（Google Apps Script + Google スプレッドシートの自動予想パイプライン）を、
既に稼働実績のある「PROJECT_EV」（SQLite × Python × LightGBM の投資型競馬AI）と同じ技術方式で
作り替える、**新規プロジェクト**の開発指示書です。PROJECT_EVとは別のリポジトリ・別のスプレッドシート・
別のアプリとして立ち上げ、並行運用しながら回収率を比較検証します。

- 新規スプレッドシート名：**dsk_Project**
- 新規アプリ名：**dsk-project**（GitHub Pages、PROJECT_EVの `daisha666.github.io/project-ev-app/` と同形式）
- 新規GitHubリポジトリ名：**daisha666/dsk-project**（提案。命名は開発時に確認）

## 1. 背景・なぜこのプロジェクトをやるか
- 「競馬予想2」は現在GASで自動化されているが、**スコア計算ロジックが実はアプリに反映されていない**。
- 開発者（ユーザー）が独自に、素点の総合力（AC列）とは別に、**オッズを反映した最終指数（AK列）**を
  並行計算して検証していた。オッズを反映させてから単勝の的中率が大きく上がり、
  単勝のみで回収率100%を超えている可能性がある、という手応えを得ている。
- 一方、並行稼働中の PROJECT_EV は方法論的に安定しているが、単勝回収率が91.4%程度で頭打ちになっている
  （7フォールド検証、1勝クラス以上・EV最大1頭のみ購入で回収率111.16%まで改善した実績はあるが、
  さらなる伸びしろを模索中）。
- そこで、**「オッズを重視する」という競馬予想2の知見を、PROJECT_EVの厳密な方法論（リーケージ防止・
  ウォークフォワード検証・過剰最適化回避）に載せ替えた新プロジェクト**として dsk_Project を立ち上げ、
  PROJECT_EVと並行運用しながらどちらが優位か検証する。

## 2. 既存「競馬予想2」のロジック分析結果（そのまま参考にする）

### 2.1 データ取得
- Yahoo競馬（sports.yahoo.co.jp/keiba）から出走表・結果・払戻金を取得
- netkeiba（db.netkeiba.com）から血統（父・母父）・過去成績（着順・上がり3F・通過順位）を取得
- ittai.net から騎手・調教師のリーディング成績（複勝率）を取得

### 2.2 特徴量（8項目、レース内でMin-Max正規化してからcondition_masterの重み%を掛ける）

| 項目 | 元データ | 備考 |
|---|---|---|
| 上がり力 | 過去5戦平均3F | 速いほど高得点になるよう反転して正規化 |
| 脚質力 | 脚質（逃げ/先行/差し/追込） | 正規化ではなく脚質区分ごとの重み値をそのまま代入 |
| 騎手力 | 騎手複勝率 | |
| 距離力 | 距離複勝率 | |
| 回り力 | 回り複勝率 | |
| 安定力 | 全成績連対率 | |
| 血統力 | 種牡馬複勝率 | |
| 調教師力 | 調教師複勝率 | |

- 重みは「競馬場×芝orダ×距離」の組み合わせ（271パターン）ごとに condition_master シートで管理
- 総合力 = 8項目の合計 ×（1 + 脚質別ペースバイアス補正）
  - ペースバイアス補正はレースごとのペース予想（スローペース想定なら差し・追込に加点、など）

### 2.3 オッズ反映後の最終指数（★これが今回の核心・要組み込み）

```
=IFERROR(AC5*(1/IF(R5="",999,R5))*8,"")
```

- AC5 = 素点の総合力、R5 = オッズ
- 「オッズが低い（人気馬）ほど倍率が大きくなる」設計
- この値をレース内で降順に並べ替えて順位化したものが最終的な印（◎○▲△☆）の基準候補

### 2.4 今回の設計方針（B案で確定）
- 印（◎○▲△☆）の決定は **オッズ反映後の順位を基準** とする
- ただし **素点ベースの順位（オッズ反映前）も並行してログに記録** し、
  どちらの方式が実際に回収率が良いか継続比較できるようにする
- PROJECT_EVの用語でいう「モデル自信度（◎）」と「賭ける価値（EV）」を分けて記録する考え方と同じ

## 3. 技術方針（PROJECT_EVを踏襲）
- 技術スタック：SQLite × Python × LightGBM（GASベースの既存システムとは別スタック）
- 開発方針：確率・期待値ベースで判断し、バックテストで検証しながら改善するデータドリブンな方針
- リーケージ防止を徹底（対象レースより前の情報のみを特徴量に使う）
- 市場情報（オッズ・人気）を除外したモデルでも判別力が残るか（＝市場に対するエッジがあるか）を検証する
  → ただし本プロジェクトでは、逆に**オッズを積極的に特徴量として取り込む**方向で検証する点が
  PROJECT_EVとの明確な違い。両者を比較すること自体が実験目的。
- ウォークフォワード検証（日付分割・複数フォールド）でバックテスト
- 大穴バイアス・過剰最適化に注意（オッズ上限フィルタの検討）

## 4. 開発ステップ（PROJECT_EVのStage1〜3を踏襲）

### Stage 1（土台）
- SQLiteでデータベース設計（races, entries, results, horses, payouts 等のテーブル）
- 無料データソースからの収集基盤構築（Yahoo競馬・netkeiba・ittai.net）
- 特徴量生成：既存8項目相当（上がり力・脚質力・騎手力・距離力・回り力・安定力・血統力・調教師力）に加え、
  **オッズ由来の特徴量（人気、単勝オッズ、オッズ反映後スコア相当の特徴量）を明示的に追加**
- 障害レース・新馬戦（過去データ0の馬）は学習・バックテスト対象から除外

### Stage 2（AI）
- LightGBMで学習（単勝中心、必要に応じて複勝も）
- 日付分割・複数フォールドのウォークフォワード検証
- オッズを特徴量に含めたモデル（本プロジェクトの主眼）と、除外したモデルの比較検証
- ハイパーパラメータチューニング

### Stage 3（投資AI）
- 期待値（EV）ベースの購入判定ロジック
- オッズ上限フィルタ等で大穴バイアスに対処
- 単勝を主軸に、複勝・ワイド・馬連は参考指標として検討（PROJECT_EVの知見を踏襲しつつ、
  実際の検証結果次第で方針変更もあり得る）

### アプリ・スプレッドシート
- スプレッドシート「dsk_Project」：操作パネル（自動実行トリガー）＋検証結果（成績サマリー・グラフ）の
  シンプルな2タブ構成（PROJECT_EVで到達した「複雑化を避けるシンプル構成」を最初から採用）
- アプリ「dsk-project」（GitHub Pages）：PROJECT_EVアプリの構成（レース条件→展開予想→
  予想カード→期待値上位→買い目推奨→全馬スコア一覧）を踏襲しつつ、
  「素点ベース順位」と「オッズ反映後順位」を両方表示できるようにする
- 自動化：Windowsタスクスケジューラでのポーリング等、PROJECT_EVと同じ運用方式を踏襲

## 5. 検証すべき問い（このプロジェクトの目的そのもの）
1. オッズを特徴量として明示的に組み込んだモデルは、PROJECT_EVの現行モデル（単勝回収率91.4%、
   1頭のみ購入で111.16%）を上回るか
2. 素点ベース順位とオッズ反映後順位、どちらを印の基準にする方が回収率が高いか
3. 「オッズ反映度合い（×8という係数含む）」は最適か、チューニングの余地はあるか
